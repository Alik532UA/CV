# AGENTS.md — контекст проєкту CV-svelte

> **Спершу прочитай [PROJECT-CONTEXT.md](PROJECT-CONTEXT.md).** Там персональний
> шар інструкцій v8: профіль, реєстр префіксів сховищ на спільному origin,
> прийняті рішення з датами, свідомі відхилення від пакета й перелік того, що в
> цьому проєкті НЕ перевіряється автоматично. Цей файл — коротка витримка для
> щоденної роботи.

## Архітектура
- **Фреймворк:** SvelteKit 2 + Svelte 5 (Runes).
- **Стейт-менеджмент:** Патерн "Контролери" у `src/lib/controllers/`. Файли мають суфікс `.svelte.ts`.
- **Сховище:** Патерн **Storage Facade** у `src/lib/services/storage.ts`. Прямий доступ до `localStorage` заборонений.
- **AI:** запити йдуть у Cloudflare Worker-проксі (`worker/`), ключі провайдерів — його секрети. Реєстр моделей — `src/lib/config/aiProviders.ts`, ланцюжок і cooldown — `src/lib/services/aiChain.ts`, формати запитів — `aiWire.ts`, промпт — `aiPrompt.ts`. Ці чотири файли імпортує і сайт, і воркер, тому в них лише відносні шляхи, без `$lib`.

## Стратегія `data-testid` у production

**B — зберігати.** Плагіна, який вирізав би атрибут на етапі збірки, у проєкті
немає, отже де-факто вибрано B — і це записано, а не вдається за A
(TESTID-AND-NAMING-v8 § 1.11). Наслідки, з якими це рішення живе: локатори видно
у продакшн-версії (+0,5–2 КБ gzip і видима внутрішня структура), зате
smoke-тести можна писати проти живого сайту без окремої staging-збірки.

Якщо колись з'явиться плагін видалення — атрибут прибирається **лише** при
`mode === 'production'`, а для `staging`/`preview` лишається, і цей розділ
оновлюється разом із кодом.

## Конвенції
- **Префікс сховища:** Усі ключі в `localStorage` мають префікс `cv-svelte_`.
- **Іменування:**
  - Компоненти: `PascalCase.svelte`
  - Контролери: `PascalCase.svelte.ts`
  - Сервіси/Утиліти: `camelCase.ts`
- **Тестування:**
  - Unit: Vitest (колокація з кодом).
  - E2E: Playwright (папка `tests/`).

## Правила (Anti-Patterns)
- **НЕ ВИКОРИСТОВУЙ** `localStorage` прямо. Тільки через сервіс `storage`.
- **НЕ ВИКОРИСТОВУЙ** Svelte 4 APIs (`writable`, `on:click`). Тільки руни (`$state`, `onclick`).
- **НЕ СТВОРЮЙ** скрипти в корені. Використовуй папку `scripts/`.
- **НЕ КЛАДИ** ключі AI у `PUBLIC_*` змінні. Сайт статичний — усе з бандла видно у DevTools; ключі тільки в секретах воркера.

## Локальні пастки

| Пастка | Що саме |
|---|---|
| Три власні порти | dev **5199** (`cv-dev`), Playwright **5299**, прев'ю зібраного сайту **5399** (`cv-preview`) — усі зі `--strictPort`. На 5173 висять усі сім проєктів |
| Клік у e2e одразу після `goto()` | до гідрації `onclick` не навішаний: клік минає повз застосунок мовчки, а падає вже очікування панелі. Пара «клік + очікування» під `toPass` |
| Голий шлях `/CV/` англійський | рядки інтерфейсу в e2e беруться зі словника `en`, а не з літералів: локаль Playwright типово `en-US` |
| Сорок дві локалізації | правка одного ключа означає правку сорока двох файлів. Перед додаванням ключа перевір, чи не існує він уже |
| Воркер має власний `tsconfig` | `npm run check` його **не** зачіпає. Для `worker/` є окремий `npm run check:worker` — без нього помилки типів там не видно ніде |
| Чотири файли спільні для сайту й воркера | `aiProviders.ts`, `aiChain.ts`, `aiWire.ts`, `aiPrompt.ts` імпортує і сайт, і воркер, тому в них **лише відносні шляхи**, без `$lib`. Аліас зламає збірку воркера |
| Частину дефектів видно лише у `build/` | для цього є `npm run check:build` окремо від `check` |

## Команди перевірки

```
npm run check         # svelte-check, має бути 0 помилок
npm run check:worker  # типи Cloudflare Worker — окремий tsconfig
npm run lint          # eslint
npm run test:unit     # Vitest
npm run test:e2e      # Playwright
npm test              # unit + e2e разом
npm run build         # збірка
npm run check:build   # гейт над build/ — порожні сторінки, секції, canonical, lang/dir
npm run check:bundle  # бюджет початкового JS над build/
```

**Результат треба побачити, а не припустити.** Твердження «правило виконано»
робиться після прогону, а не замість нього (AI-AGENT-PITFALLS-v8 § 5.1).

## Бази, які рухаються лише вниз

Три гейти проєкту працюють не від нуля, а від зміряного числа — бо нуль там
довелося б вимкнути назавтра, а вимкнений гейт гірший за відсутній.

| База | Файл | Що означає |
|---|---|---|
| Порушення axe | `tests/a11y-baseline.ts` | зараз 0 у чотирьох ключах (`home`, `homeDark`, `betaChecklist`, `aiModal`) |
| Замалі сенсорні цілі | `tests/touch-target-baseline.ts` | 21 на сайті, 0 на сторінці чеклиста: правило 44×44 не перевіряв ніхто, і це перший вимір |
| Файли понад межу § 7 | `src/structure-conventions.test.ts`, `ALLOWED` | 11 файлів із числом рядків; найбільший — 1073 |

Правило спільне: **число можна тільки зменшувати**, і зменшується воно разом із
правкою, що його спричинила. Перелік поіменний, тому НОВА знахідка валить прогін
навіть у межах числа. Побачивши червоне — виправляй причину, а не число.

## Чеклист ручної перевірки

`/beta-test-checklists/` — те, чого не перевіряє жоден автотест: прохід
клавіатурою й читалкою, перший кадр теми, RTL на івриті, поведінка на
справжньому телефоні. Сторінка службова: `noindex`, немає в sitemap, немає в
меню, `Disallow` у `robots.txt` — і всі чотири боки перевіряє `check:build`.

- **Пункти — дані**, `src/lib/data/betaChecklist.ts`, дві мови в одному об'єкті
  (у 42 словники вони не йдуть: правка одного пункта коштувала б 42 правок).
- **Позначка несе версію збірки.** З іншої версії — видима, підписана й у
  поступі не рахується: інакше галочка з-перед сорока комітів виглядає як
  сьогоднішня.
- **За пунктами стежить `src/beta-checklist-canon.test.ts`**: `covered` мусить
  називати наявний файл тесту, «натисніть» — наявний локатор, у кожної вкладки
  мусить бути пункт для людини й пункт-межа «не мусить». Пункт, що відстав від
  коду, — це не борг, а дезінформація.
- **Додаючи маршрут, додай вкладку**: інваріант бере перелік маршрутів із диска
  й падає на сторінці, яку нічим перевіряти.
